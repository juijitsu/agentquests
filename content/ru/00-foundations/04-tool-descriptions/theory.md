# Теория · Инструмент продаётся описанием

Когда вы даёте агенту инструмент, модель получает о нём ровно три вещи:

```python
{
    "name": "check_border_status",
    "description": "Показывает очередь и время ожидания на погранпереходе.",
    "parameters": {"crossing": "string"},
}
```

Имя, описание и схему параметров. **Ваш код она не видит никогда.** Ни тела
функции, ни того, откуда берутся данные, ни комментариев рядом.

Значит выбор инструмента — это выбор по описанию и только по нему. Два инструмента
с похожими описаниями модель будет путать, как путал бы человек, которому дали
два одинаковых ярлыка.

## Описание — это код

Отсюда мысль, к которой трудно привыкнуть: **описание инструмента является
частью программы, а не комментарием к ней.** Строка в кавычках определяет
поведение системы так же прямо, как условие в `if`.

Из этого следует неприятное. Компилятор не проверит описание. Тесты, которые
дёргают функцию напрямую, тоже пройдут — они ведь не читают описаний. Код
собирается, всё зелёное, а агент выбирает не тот инструмент.

**Девять из десяти случаев «агент тупой» — это проблема описания**, и чинится
она за две минуты правкой текста.

## Что делает описание хорошим

Три вещи, и все три про модель, а не про читателя кода:

**Случай применения.** Не «что делает функция», а «когда её звать». Модель
выбирает из нескольких — ей нужен признак, по которому отличить.

**Допустимые значения.** Перечислите их прямо в описании. Это сокращает выдуманные
аргументы вернее любой валидации.

**Слова предметной области.** Пользователь спросит «сколько ждать на переходе» —
пусть эти же слова будут в описании. Модель сопоставляет запрос с описанием.
